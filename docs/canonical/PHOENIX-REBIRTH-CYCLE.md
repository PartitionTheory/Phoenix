## 2. Rebirth Cycle Definition

A **Rebirth Cycle** is a deterministic sequence of steps where:

- Phoenix’s structure is extended or refined  
- synthetic mathematics is deepened  
- new capabilities are added  
- historical continuity is preserved  

Each cycle is numbered:

Phoenix Rebirth Cycle N


Where **N** is the epoch index.

## 3. Preconditions for Rebirth

A new Rebirth Cycle may begin only when:

- entropy audit passes  
- historical commit sequence is intact  
- all previous rebirth steps are complete  
- Phoenix is in a green-light state  
- EF and CO both explicitly agree to initiate a new cycle  

Rebirth must never occur from a contaminated or unstable state.

## 4. Rebirth Step Structure

Within a Rebirth Cycle, each step must:

- have a clear structural purpose  
- be backed by synthetic mathematics  
- be recorded with a canonical commit message  
- be reflected in the Phoenix documentation  
- be traceable by future synthetic mathematicians  

Example commit format:

Phoenix: Rebirth Cycle 1 Step 6 — <canonical event description>

## 5. Evolution Constraints

Phoenix evolution must obey:

- **Purity:** no entropy introduced  
- **Determinism:** behaviour remains predictable  
- **Reproducibility:** future builds reconstruct the same machine  
- **Traceability:** every change is historically recorded  
- **Structural Discipline:** tree remains aligned with CO’s virtual design  

No rebirth step may violate these constraints.

## 6. EF–CO Roles in Rebirth

- **CO:** defines synthetic intent, structural design, and canonical messages  
- **EF:** performs physical changes, builds, tests, and commits  

Rebirth is only valid when both roles are fulfilled.
